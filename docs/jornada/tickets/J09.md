## Objetivo

Escrever **os arquivos** de migration que criam o armazenamento da Jornada. **Escrever, não
aplicar.** Aplicar (até em homologação) é do humano.

## Pré-requisito

`docs/jornada/spec-sua-jornada.md` existe e J08 está fechado. **Se a spec não existe, pare
imediatamente** — não deduza o schema do protótipo.

## A regra que manda em tudo aqui

**Só contadores e selos. Nunca um diário.** Não existe tabela que registre "em 14/10 ela
lançou uma despesa". Isso seria uma linha do tempo do trabalho dela, e o público deste app
é mulheres pra quem discrição é o produto. Se o schema que você desenhou permite
reconstruir o que ela fez em cada dia, **o schema está errado**.

O limite diário precisa funcionar sem diário. A forma de fazer isso é guardar, por ação,
apenas **a data do último ganho e quantas vezes naquela data** — e sobrescrever quando o
dia vira. Sem histórico acumulado.

## Escopo — e só isto

- `supabase/migrations/00NN_jornada_contadores.sql` (e mais arquivos `00NN_jornada_*.sql` se
  precisar)

**Nada mais.** Nenhum arquivo de `components/`, `lib/` ou `app/`.

## Numeração

A última migration aplicada é `0033_rede_fotos_otimizacao.sql`. A próxima livre é **0034**.
**Antes de criar o arquivo**, rode:

```bash
ls supabase/migrations | tail -5
git fetch origin && git log --oneline origin/mockuptesterede -5 -- supabase/migrations
```

Se outra branch já pegou o número, pegue o seguinte **e avise no PR**. Isso já aconteceu
neste repositório: dois PRs colidiram no mesmo número e um teve que ser renumerado na mão.

## O que a migration precisa cobrir

Derive os nomes e colunas da spec, mas ela tem que guardar ao menos:

- o total de **Glow** e o **estágio** atual da usuária;
- o Glow por **pilar** (Organizar, Prosperar, Proteger, Conectar);
- por ação: **contagem total**, mais `data_ultimo_ganho` e `ganhos_no_dia` (só isso — é o
  que faz o limite diário funcionar sem diário);
- os **selos**, com o nível atual de cada um;
- o **capítulo do mês**: mês/ano, progresso de cada uma das 3 missões, e se fechou;
- a **coleção de enfeites** (quais meses foram fechados);
- os **marcos de dinheiro** já batidos;
- as **preferências**: som ligado/desligado, Modo discreto, e o opt-in de mostrar estágio e
  selos no perfil público (**padrão: desligado**).

## RLS — obrigatório

**Toda** tabela nova nasce com RLS ligada e política de que a usuária só lê e escreve a
própria linha. Nenhuma tabela da Jornada é legível por outra usuária, **com uma exceção**: o
que ela marcou como opt-in pra perfil público. Essa exceção precisa ser uma política
explícita e separada, nunca um `select` aberto na tabela toda.

Já houve um furo de permissão em RPCs neste repositório (achado e corrigido nas fotos do
feed). **Escreva as políticas pensando que alguém vai tentar ler a linha de outra pessoa.**

## Aceite

- [ ] A migration é **aditiva**: nenhuma tabela ou coluna existente é alterada ou removida.
- [ ] Toda tabela nova tem RLS **ligada** e política por usuária.
- [ ] O opt-in de perfil público é uma política separada e explícita.
- [ ] Nenhuma tabela permite reconstruir o que a usuária fez em cada dia.
- [ ] A migration roda numa base limpa do zero (`supabase start` local) **sem erro**.
      Documente no PR o comando que você usou e a saída.
- [ ] `npm run typecheck` e `npm test` passam.
- [ ] No PR: o número de migration escolhido, e a confirmação de que ele estava livre no
      momento do PR.
- [ ] **Nada foi aplicado em homologação nem em produção.** Diga isso no PR.
- [ ] PR pra `feature/jornada`. **Não mergear.**

## Para o humano, depois do merge

Aplicar em **homologação** primeiro (projeto `jobapp-homologacao`, `pmrnpbwlddzgcyaqexap`).
Nunca direto em produção. Antes de tocar produção, backup.

> Ao colar SQL no editor do Supabase pelo Chrome: **desative a tradução automática da aba
> antes**. Com ela ligada, a query trava ou é corrompida.
